## 1. Scope A - internal deterministic reproducibility

**Static scan of `src/`:** randomness appears only in `hourly_model.bootstrap_curve_params` (`np.random.default_rng(seed)`, seed 0 by default) and, in the reference-only branch, `calibration.bootstrap_calibration_ci` / `projection` (seed 0, never run by the orchestrator). There is no `random`, `np.random.seed`, `shuffle`, multiprocessing, threading or `n_jobs`. Degenerate bootstrap resamples are skipped deterministically (`except ... continue` on a seeded stream). No `datetime.now`/`uuid`/`getpid` in the modelling modules (timestamps exist only in Stage 1 manifests, reports and the orchestrator's records, none of them inputs to `final_results`). The only `set()` uses are wrapped in `sorted(...)`. Files are iterated through `sorted(glob(...))`.

**Empirical test run for this design** (real database, `--skip-stage1`, all three downstream stages forced): run 1 with `PYTHONHASHSEED=1` and one BLAS thread (`OMP/OPENBLAS/MKL_NUM_THREADS=1`); run 2 with `PYTHONHASHSEED=987654` and default threading; both compared with the files that were already on disk. The 13 files compared (`final_results.csv/.parquet`, the sensitivity companion, `pte_curtailment_option_E.parquet` + sidecar, the four `hourly_curve_*.json`, `hourly_base_profile.parquet`, `hourly_horizon_bands.json`) have **identical MD5 in all three states**. Together with the Task 14-2 live recompute, this is four byte-identical recomputations on one machine.

**What is and is not guaranteed.** Guaranteed (and tested, 4.1): same environment, same inputs, same machine, different hash seed or thread count -> byte-identical. Not guaranteed and not claimed: bitwise identity across operating systems, CPUs, BLAS builds or library versions (parquet files embed the pyarrow version, `to_csv` follows the platform line ending, floating-point reductions may differ in the last bits). The cross-platform promise is therefore the one the orchestrator already enforces: `final_results` reproduces `reference_totals.json` within relative 1e-9.

## 2. Scope B - environment reproducibility (state re-verified)

- `requirements.txt` (17 lines): **floors only** (`pandas>=2.2`, `numpy>=1.26`, `scipy>=1.12`, `pyarrow>=16.0`, `statsmodels>=0.14`, `ruff>=0.4`, ...), runtime and dev packages mixed. `pyproject.toml`: the same floors, split into `dependencies` and `[dev]`; `requires-python >= 3.10`. No lock file, no constraints file.
- **What actually runs:** local `.venv` Python 3.11.9 with pandas 3.0.6, numpy 2.4.6, scipy 1.17.1, pyarrow 26.0.0, statsmodels 0.15.0, pydantic 2.14.1, ruff 0.17.1, pytest 9.1.1; CI (run 40528102587) Python 3.11.17 on Linux with pytest 9.1.1, resolving the newest releases at each run. Python 3.10 is declared and never tested; all results were produced with the local set above.
- **Risk:** every CI run and every fresh install resolves different versions (the pandas 3 dtype test failure of Task 13_pre was exactly this kind of drift); a reader in 2027 may get other numbers or errors.
- **Proposal (no pip-tools, no new tooling): an exact lock file `requirements.lock.txt`** produced once from the verified environment with `pip freeze` (all direct and transitive packages, `==` pins), filtered of editable and platform-only entries, with a header recording Python 3.11.9, OS and date. Installation for reproduction: `pip install -r requirements.lock.txt && pip install -e . --no-deps`. `requirements.txt` and `pyproject.toml` stay as the human-readable floors (so the Task 14 consistency test, which compares the package names of `requirements.txt` with `pyproject.toml`, is untouched: the lock has a different name and is outside that test). New tests: every package declared in `pyproject.toml` has an `==` pin in the lock; no unpinned line; the lock's Python version header is the one CI uses. CI keeps testing the floors resolution (as now) and gets one extra job installing the lock and running the unit tests (answers "does the pinned environment still work"), about two minutes. Rejected: pip-tools/uv/poetry (new tool, new workflow, no benefit for a single-machine research repository), Docker (heavier than the claim needs, deferrable).
- Migration: generate the lock, add it plus its tests and the CI job, add one paragraph to `docs/reproducibility.md`; nothing else changes.

## 3. Scope C - methodological reproducibility for an external reader

**State:** no single document exists. The path from raw data to final numbers is spread over `docs/methodology.md` (chronological sections 2.3 to 2.3k, with the current model in 2.3j buried mid-file and the original Step 1/Step 2 text of 2.3 and 2.4 still describing the superseded national C(P)), `docs/orchestration.md` (how to run), `docs/roadmap.md` (decisions D1-D12 table, updates by task), `docs/claude_commands.md` (task history), `config/discovered_sources.yaml` (D13-D32 and the adopted texts) and `README.md` (stale, section 4). A reader would have to reconstruct Tasks 7-14.

**Proposal: `docs/reproducibility.md`**, for a reader who already has `curtailmit_database` populated (or will populate it by Stage 1); it makes no promise of data availability beyond what D33 decides and says so in its first section. Outline:
1. Scope and limits: what is reproduced (the 156-row `final_results`), what is promised (section 1 of this design), the data-availability statement per D33, what is not covered (figures until 13B).
2. Environment: Python, lock file, install commands (from Scope B).
3. Data: sources, how Stage 1 acquires them, the snapshot manifest, the `END_EXCLUSIVE` cutoff and why October 2026 is excluded.
4. Run: `curtailmit-run` step by step, expected console output, stamps and skip logic, exit codes, reference check, the Windows/Linux notes.
5. Why this model (the only history needed): one page on D24 (hourly dose-response, option E, by-horizon treatment), D25 (accepted drift, direction upward), D26, D23, with one-line pointers to the findings documents rather than the investigation.
6. Reading the output: columns of `final_results`, range semantics (never a confidence interval), OM/CM never summed, partial uncertainty composition (D28-D30), the 2050 conditional range.
7. Decision register: D1-D34 in one table (id, topic, status, where decided), generated from the YAML and the roadmap table so the two sources cannot disagree (a test compares the table with the YAML).
8. Verification: reference totals, determinism guarantee, how to re-baseline consciously.
9. Run manifest: how to read `run_manifest_*.json`.

**Run manifest (original Task 15 item 1).** At the end of every successful run (`SUCCESS` and `SUCCESS_PARTIAL`) `curtailmit-run` writes `logs/run_manifest_<UTC>.json`: git commit and dirty flag; Python/platform and the installed version of every locked package; `END_EXCLUSIVE`; hashes of `config/*.yaml` and of the adopted decisions used; for every raw file used by the run its retrieval manifest data (source URL, retrieval time, SHA-256, size, verified against the file at write time); stage statuses with reasons; hashes of processed and output artifacts; the reference-check result; the path of the existing `pipeline_run_*.json`. A failed run keeps writing only `pipeline_run_*.json` (no manifest of a failed run). A derived, repository-friendly `data_snapshot_manifest.json` (the raw-file part only) is written by a small command and is what D33 option 1 would commit. Files are written next to the existing logs; nothing in the modelling path changes.

## 6. Test plan for the implementation

1. **Determinism (unit, in CI):** `run_hourly_calibration` + `project_curtailment_hourly` on the committed fixture panel (`tests/fixtures/option_e/hourly_sample_2025H1.csv` or a synthetic panel) twice in one process and once in a subprocess with a different `PYTHONHASHSEED` and one BLAS thread: byte-identical files. A source scan asserts the only RNG construction in the production modules is `default_rng(seed)` with an explicit seed argument and that no module uses `random`, `np.random.seed` or `shuffle`.
2. **Determinism (integration, local):** forced recompute of calibration -> results with two hash seeds; MD5 of the 13 files equal; this formalises what this design did by hand.
3. **Lock file:** every package in `pyproject.toml` pinned with `==`; no range operator; header Python version 3.11; `requirements.txt` vs `pyproject.toml` test (Task 14) unchanged and passing; CI job `unit-tests-locked`.
4. **Run manifest:** unit tests with the mocked stages of `tests/test_pipeline.py`: manifest written on success and partial runs, not on failure; raw-file entries verified against their retrieval manifests (a tampered file makes the manifest step fail with the existing gate semantics); contains commit, dependency versions, `END_EXCLUSIVE`, decision and config hashes; no network.
5. **Snapshot manifest** (if D33 option 1 or 2): generated twice from the same database gives identical content apart from the timestamp field.
6. **Documentation:** a test that the decision register in `docs/reproducibility.md` equals the YAML ids and statuses; a test that every `docs/*.md` link to another `docs/` file resolves; `docs/acceptance_criteria_status.md` has one row per criterion of roadmap section 7 and every referenced test name exists.
7. Suite stays green with an empty `DATABASE_ROOT`; `ruff` clean.
